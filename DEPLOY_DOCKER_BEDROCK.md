# Deploying with Docker + Amazon Bedrock (EC2)

This is an alternative to `DEPLOY_AWS.md`: same EC2 instance, but the app
runs inside a Docker container instead of a bare Python venv, and answers
are generated by **Amazon Bedrock** (Claude, run by AWS) instead of Gemini.

Your code didn't change in a way that breaks the old path — `GENERATION_BACKEND`
in `.env` picks Gemini or Bedrock at runtime, so you can still use
`DEPLOY_AWS.md`'s venv approach with Gemini if you'd rather. This guide
covers the new combination specifically.

## Why this setup

- **Docker** — `docker build` + `docker run` is now the entire install
  step. No more "works on my machine but not the server" dependency
  mismatches, and updating the app later is `docker build` + restart the
  container instead of re-running pip installs by hand.
- **Bedrock instead of Gemini** — no separate API key to manage at all.
  On EC2, an IAM role attached to the instance gives the container
  permission to call Bedrock automatically — nothing secret sits in `.env`.
- **Still just one EC2 instance** — same reasoning as before: this app
  keeps its index in memory and on local disk, so a single instance is the
  simplest correct architecture. Docker here is about clean deployment, not
  about scaling to multiple instances (that's an ECS/Fargate step later).

## Step 1 — Bedrock model access

AWS recently changed this: foundation models are now **auto-enabled
account-wide the first time you invoke them** — there's no more manual
"Model access" approval page to click through.

The one exception: **Anthropic models may still need a one-time use-case
submission** the very first time your account calls one, via AWS
Marketplace. If your first `/query` request fails with something
mentioning marketplace permissions or use-case details, that's what's
happening:

1. Go to the [Bedrock Console](https://console.aws.amazon.com/bedrock/) →
   **Model catalog**
2. Find **Claude 3.5 Haiku**, open it
3. If prompted, submit the brief use-case form (a few sentences on what
   you're building is enough — this project is a fine description)

After that one-time step (if it's even required for your account), calling
the model from your app just works — no separate approval to wait on.

## Step 2 — Launch the EC2 instance

Same as before, with one addition — an **IAM role** so the instance can
call Bedrock without any access keys:

1. **IAM Console** → **Roles** → **Create role**
   - Trusted entity: **AWS service** → **EC2**
   - Permissions: search for and attach `AmazonBedrockFullAccess` (or for
     tighter scope, create a custom policy allowing just
     `bedrock:InvokeModel` and `bedrock:Converse` on the specific model ARN)
   - Name it `rag-project-bedrock-role`, create it
2. **EC2 Console** → **Launch instance**, same as `DEPLOY_AWS.md` Step 1
   (Ubuntu 22.04, `t3.small`, security group with SSH from My IP + custom
   TCP 8000 from Anywhere), **except**:
   - Under **Advanced details** → **IAM instance profile**, select
     `rag-project-bedrock-role`
3. Launch.

## Step 3 — Install Docker on the instance

Connect via **EC2 Instance Connect** (EC2 Console → select instance →
Connect → EC2 Instance Connect), then:

```bash
sudo apt update
sudo apt install -y docker.io
sudo systemctl enable --now docker
sudo usermod -aG docker ubuntu
```
Log out and reconnect once (so the group change takes effect) before
running `docker` commands without `sudo`.

## Step 4 — Get your project onto the instance

Same options as before:

```bash
# Option A: GitHub
git clone https://github.com/yourusername/rag_project.git
cd rag_project

# Option B: upload the zip, then on the instance:
sudo apt install -y unzip
unzip rag_project.zip -d rag_project
cd rag_project
```

## Step 5 — Configure `.env` for Bedrock

```bash
cp .env.example .env
nano .env
```
Set:
```
GENERATION_BACKEND=bedrock
AWS_REGION=us-east-1
BEDROCK_MODEL_ID=anthropic.claude-3-5-haiku-20241022-v1:0
```
Leave `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` out entirely — the IAM
role from Step 2 supplies credentials automatically inside the container
(Docker forwards the instance's IAM role through to `boto3` for free, no
extra config needed).

Set (in addition to the Bedrock settings above):
```
INDEX_PATH=/app/data/index.pkl
DOCS_FOLDER=/app/data/sample_docs
```
This is what makes the `-v $(pwd)/data:/app/data` mount below actually
persist your index and uploaded documents across container rebuilds —
without it, they'd live inside the container's own filesystem and vanish
every time you `docker rm` and recreate it.

## Step 6 — Build and run the container

```bash
docker build -t rag-project .

docker run -d \
  --name rag-app \
  --restart unless-stopped \
  -p 8000:8000 \
  --env-file .env \
  -v $(pwd)/data:/app/data \
  rag-project
```

What each flag is doing:
- `--restart unless-stopped` — the container survives instance reboots,
  same job `systemd` did in the venv-based guide
- `--env-file .env` — passes your Bedrock/region/path settings in
- `-v $(pwd)/data:/app/data` — mounts a host folder to `/app/data`, which
  is where `INDEX_PATH`/`DOCS_FOLDER` from Step 5 now point

## Step 7 — Test it

```bash
docker ps                 # confirm it's running
docker logs -f rag-app    # watch logs, e.g. to debug a Bedrock error
```
Then visit `http://<public-ip>:8000` in your browser, same as before.

## Updating the app later

```bash
git pull                  # or re-upload the zip
docker build -t rag-project .
docker stop rag-app && docker rm rag-app
docker run -d --name rag-app --restart unless-stopped -p 8000:8000 \
  --env-file .env -v $(pwd)/data:/app/data rag-project
```

## Troubleshooting

- **`AccessDeniedException` calling Bedrock** → most likely Step 2 (IAM
  role not attached to the instance, or missing `bedrock:Converse`
  permission). If the error specifically mentions marketplace or use-case
  details, go back to Step 1 — some Anthropic models need that one-time
  form submitted before your account's first call succeeds.
- **`ValidationException: model identifier is invalid`** → some Bedrock
  models require a *cross-region inference profile ID* instead of the
  base model ID (e.g. `us.anthropic.claude-3-5-haiku-20241022-v1:0` with a
  `us.` prefix rather than the bare model ID). If the plain ID in
  `.env.example` gets rejected, check the model's page in the Bedrock
  Console for the exact ID it expects.
- **Container starts then immediately exits** → run `docker logs rag-app`
  (no `-f`) to see the crash traceback; usually a missing/malformed `.env`.
- **Works locally, fails on EC2 specifically** → almost always the IAM
  role. Locally, `boto3` was probably picking up credentials from
  `aws configure` on your machine; on EC2 it relies entirely on the
  instance profile from Step 2.
